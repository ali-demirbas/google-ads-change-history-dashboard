**Audited artifact:** `ads_change_history.py` (1768 lines) + `SKILL.md`
**Audit date:** 2026-08-18
**Reference standard:** Google Ads API v17-equivalent proto definitions for `ChangeEvent`,
`ChangedResource`, `ChangeEventResourceType`, `ChangeClientType`, `ResourceChangeOperation`,
independently re-verified this session against Google's own generated field/enum
documentation (not taken from any prior summary, including this auditor's own prior
statements in this conversation — one of which is corrected below, see F-03 note).

**Method:** full line-by-line reading of the audited file + 23 empirical reproductions run
against the actual code (not inspection alone). Every EVIDENCE line below is either a
direct code excerpt with a line number, or the literal output of a reproduction run in
this session.

## Findings

### F-01
**SEVERITY:** P0 — two verifiably distinct, real events are irreversibly merged; this is
data loss, not miscategorization.
**CATEGORY:** Data Integrity / Identity
**LOCATION:** `ads_change_history.py`, `make_change_id()` L635-637, `dedupe_rows()` L752-769
**EXPECTED:** The dedup key should not merge two events that Google's own model
distinguishes by a unique `resource_name` (event ID).
**ACTUAL:** `change_id` hashes only `(account, timestamp-as-given, user, resource, field,
old, new)` — it does not include `source_event_id`. `dedupe_rows()` drops any row whose
`change_id` was already seen, without consulting `source_event_id`.
**EVIDENCE:** Two input rows differing only in `resource_name`
(`customers/1/changeEvents/1~1~0` vs `...~1~2~0`, otherwise identical
account/timestamp/user/resource/field/old/new) were run through `run_pipeline()`. Result:
`row_count: 1`, `duplicates_removed: 1`. The surviving row's `source_event_id` is
`...~1~1~0` — the second event is absent from every output file.
**IMPACT:** Any two real events sharing account, same-second timestamp, user, resource,
field, and old/new values are silently and permanently merged, even when `source_event_id`
proves they are different events.
**STATUS:** FAIL

### F-02
**SEVERITY:** P0 — unhandled crash, total pipeline failure, on a data shape the codebase's
own documentation implies it accepts.
**CATEGORY:** Functional / Google Ads API Semantics
**LOCATION:** `ads_change_history.py`, `match_structured()` L778; root cause
`normalize_changes()` L714 (`field_name = g("field_name")`, no type normalization)
**EXPECTED:** Per Google's model, `changed_fields` is a `FieldMask` — a repeated field
(list of paths) when one event touches multiple fields.
**ACTUAL:** `field_name` is assigned the raw JSON value with no type check. If the source
provides a JSON list, it flows unchanged into `field_name`, and `match_structured()` calls
`.lower()` on it.
**EVIDENCE:** Input row with `"changed_fields": ["status", "name"]` →
`AttributeError: 'list' object has no attribute 'lower'`, raised at L778, propagates
uncaught out of `run_pipeline()`.
**IMPACT:** Any already-"flattened" JSON that still represents `changed_fields` in its
natural repeated-field JSON shape crashes the entire pipeline with a raw Python traceback,
not a structured status.
**STATUS:** FAIL

### F-03
**SEVERITY:** P0 — silently corrupts (for `campaign`) or silently drops (for `ad_group`)
data central to the tool's stated purpose ("which account/campaign/ad group").
**CATEGORY:** Data Model / Google Ads API Semantics
**LOCATION:** `ads_change_history.py`, `HEADER_ALIASES["aliases"]` L165-196,
`normalize_header()` L317-318
**EXPECTED:** Per Google's verified `ChangeEvent` model (see Reference ground truth above),
top-level `campaign`/`ad_group` fields hold resource-name-format strings identifying the
affected campaign/ad group.
**ACTUAL:** No alias entry is keyed for the literal field names `campaign`/`ad_group` as
attributed-resource identifiers. A source column literally named `campaign` is captured
only by accidental case-insensitive match against the alias list intended for a
human-readable UI column (`["Campaign", "Kampanya", "campaign.name"]`), which maps to
`campaign_name` — a field the schema and dashboard treat as a display name. A column named
`ad_group` matches nothing (`normalize_header()` does not fold underscores to spaces, so
`"ad_group"` never equals normalized `"Ad group"` → `"ad group"`).
**EVIDENCE:** Source row with Google's real field values `"campaign":
"customers/1/campaigns/500"`, `"ad_group": "customers/1/adGroups/900"` produced:
`campaign_id: None`, `campaign_name: "customers/1/campaigns/500"` (a resource path, not a
name), `ad_group_id: None`, `ad_group_name: None`.
**IMPACT:** Real `ChangeEvent`-sourced data carrying Google's own campaign/ad-group
attribution shows a raw resource path where a campaign name is expected in the dashboard,
and shows nothing at all for ad group.
**STATUS:** FAIL

### F-04
**SEVERITY:** P0 — a documented privacy control (`--mask-users`) silently does not apply
to one of the pipeline's standard, unconditionally-written output files.
**CATEGORY:** Privacy / PII
**LOCATION:** `ads_change_history.py`, `run_pipeline()` L1495-1497 (`changes.jsonl`
written from `c["rows"]` directly, before `build_dashboard()`'s masking step)
**EXPECTED:** Per `SKILL.md` ("`--mask-users`... replaces human user names/emails... for
external sharing") and the module docstring, passing `--mask-users` should prevent raw
human user identity from appearing in the run's output.
**ACTUAL:** Masking is applied only inside `build_aggregation()`, which feeds
`dashboard.html` and `change_history.json`. `changes.jsonl` is written earlier from the
unmasked rows, unconditionally, regardless of `--mask-users`.
**EVIDENCE:** Run with `mask_users=True` on a row with `user_email:
"secret.user@realcompany.example"` — string absent from `dashboard.html`, present verbatim
in `changes.jsonl`.
**IMPACT:** A user who runs with `--mask-users` specifically to redact identities before
sharing output, and shares `changes.jsonl` (a normal, undocumented-as-sensitive pipeline
artifact), leaks exactly the identities they asked to have masked.
**STATUS:** FAIL

### F-05

aggregation path (`campaign_last` / Campaign Last Changes, per the file's own inline
comment at L901-903) is present, unfixed, in two sibling aggregation paths within the same
function and its client-side JS mirror.
**CATEGORY:** Data Integrity / Aggregation
**LOCATION:** `ads_change_history.py`, `build_aggregation()` L866

**IMPACT:** The Summary panel's "Changed Campaigns" count and "Most Active Campaign" stat
undercount/conflate whenever a campaign name is reused across accounts.
**STATUS:** FAIL

### F-07
**SEVERITY:** P2
**CATEGORY:** Data Integrity / Operation Semantics
**LOCATION:** `ads_change_history.py` L719-720 (`operation = ... if operation else
infer_operation(raw_summary)`); `infer_operation()` L600-608
**EXPECTED:** A genuinely unspecified operation should not be silently converted to a
specific operation value without that being visible.
**ACTUAL:** An operation value of `""` (present column, empty string — distinct from a
missing column) is falsy in Python and is routed into `infer_operation()`, whose final
fallback is `"UPDATE"`. Explicit string values `"UNKNOWN"` and `"UNSPECIFIED"` (real Google
enum values) are, by contrast, correctly preserved unchanged — they do not hit this path
because they are non-empty strings.
**EVIDENCE:** Three rows differing only in `resource_change_operation`: `""` → normalized
`operation: "UPDATE"`; `"UNKNOWN"` → normalized `operation: "UNKNOWN"`; `"UNSPECIFIED"` →
normalized `operation: "UNSPECIFIED"`.
**IMPACT:** A row whose operation field is present but empty becomes indistinguishable
from a genuine UPDATE after normalization.
**STATUS:** FAIL (for the empty-string case only — explicit UNKNOWN/UNSPECIFIED strings
are correctly preserved, STATUS: PASS for that sub-case)

## A. Critical Findings (P0/P1)

- **F-01** (P0): Identity collision in `dedupe_rows()` silently discards distinct real
  events that share hash-relevant fields, when `source_event_id` — available and provably
  distinguishing — is not consulted.
- **F-02** (P0): `changed_fields` provided as a JSON list (the natural shape of Google's
  FieldMask) crashes the pipeline with an unhandled `AttributeError`.
- **F-03** (P0): `ChangeEvent`'s own top-level `campaign`/`ad_group` attributed-resource
  fields are either mis-mapped (campaign: a resource path stored where a name is expected)
  or entirely uncaptured (ad_group).
- **F-04** (P0): `--mask-users` does not apply to `changes.jsonl`; raw user email/name
  leaks in that file even when masking is explicitly requested.
- **F-05** (P1): The campaign/account identity-collision defect, already fixed once in
  this codebase (`campaign_last`), remains present in two sibling code paths
  (`summary.changed_campaigns`, `summary.most_active_campaign`) and their JS mirror.
- **F-11** (P1): 6 of 21 real Google resource types have zero categorization coverage.

## B. Functional Findings

- SKILL.md's currently-stated input format list (CSV/TSV/pre-flattened JSON) matches
  `read_rows()`'s actual branches — no discrepancy found (F-12, STATUS: PASS).
- TSV support and the dict-wrapped-JSON input shape are both implemented but neither is
  exercised by any test (F-13, F-23).
- Malformed inputs (empty CSV, invalid JSON, missing file) all raise unhandled, low-level
  Python exceptions rather than the structured error status the equivalent empty-JSON case
  already returns (F-16, F-17, F-18).
- Duplicate CSV headers are silently resolved by the stdlib with no detection layer of
  this codebase's own (F-19).
- Operation value `""` (present-but-empty) is treated identically to a missing operation
  column and silently normalized to `"UPDATE"`; explicit `"UNKNOWN"`/`"UNSPECIFIED"`
  strings are correctly preserved un-coerced (F-07).

## C. Data Integrity Findings

- F-01, F-03, F-04, F-05, F-08, F-10, F-11, F-20 (see above).
- Confirmed correct (STATUS: PASS): determinism across repeated runs (F-21); no value

  values preserved un-coerced (F-07, PASS sub-case); mapping-profile fingerprint collision
  behavior matches its own documentation (F-20, PASS against documentation).

All findings below were fixed in `ads_change_history.py` after this audit and
independently re-verified (code excerpt or reproduction, same standard as the original
finding). Each fix has a permanent regression test in `self_test()`.

| ID | Fix | Verified by |
|---|---|---|

| F-02 | `field_name` arriving as a JSON list (real FieldMask shape) is joined into a string and flagged `multi_field: true` instead of crashing. | Reproduction: `"changed_fields": ["status","name"]` → `status: ok`, `field_name: "status, name"`, `multi_field: true`. |

**Not fixed, by design (recorded, not silently dropped):**
- **F-06** (dead `user_id` field): left in the schema as documented-but-unpopulated. No source in this codebase provides a per-user ID (only email/name), and removing a shipped schema field is a breaking change with no current consumer benefiting from it.
- **F-10** (unreachable `CONVERSION` category rule): left in place. Verified this is a genuine Google API model limitation, not a mapping defect — `ConversionAction` is a separate GAQL resource entirely outside `ChangeEvent`'s 21 resource types, so no mapping fix can make this rule reachable from `ChangeEvent` data. Kept for `--extra-rules` use with non-ChangeEvent sources.
- **F-20** (mapping-profile fingerprint collision across semantically different same-header sources): this is `SKILL.md`'s own documented, deliberate tradeoff — not something this pass changed. The runtime-visibility gap noted in the original finding (no signal distinguishing "fresh mapping" from "reused profile" in the CLI's own printed output) is unresolved.
- **Filtering** and **Dashboard empty/malformed/large-data behavior** dimensions: still UNKNOWN — not exercised in this pass either.
